Fix a `view` model whose SQL text is unchanged (and so skips its `CREATE`/`ALTER`) going stale when something it reads changes shape - a referenced table or view gaining, losing or reordering columns, or changing a column's data type. SQL Server derives a view's column metadata - names, positions and types, including the expansion of an unqualified `select *` - at `CREATE`/`ALTER VIEW` time and caches it; skipping that statement left the cache silently out of sync with the objects the view reads, so it kept reporting the old shape under the old names and positions even though every dbt run reported success. A child view, for instance, went on reporting `varchar` after its parent view's column became `int`. The skip path now runs `sp_refreshview` against the view instead of a no-op, which re-derives that metadata from the current state of its sources without reissuing the `CREATE`; because dbt builds a view only after everything it depends on, a parent's change is already in place by the time the child refreshes. The refresh carries the model's database as a `USE` prefix, so a cross-database view model refreshes the intended object rather than erroring on a name that does not resolve in the connection's current database. Note that a metadata refresh advances the view's `sys.objects.modify_date` just as an `ALTER` would, so that column no longer distinguishes a skipped run from a rebuild.
